# AetherOS Secure Core · 安全系统设计

> 本系统**主打安全**。文档描述的是当前在这台云电脑上真实编译、真实运行、真实可测的
> 安全整机本体（`secure/`），不是设计草案。所有结论均附可复现命令与证据文件。
> 系统名 `AetherOS`；产品名「长明 Aether」、公司名「长明科技（武汉）有限公司」仅为
> **命名预留**，未注册、未对外宣称。

## 1. 定位与交付形态

在云电脑上用纯软件模拟，做出一套能开机自检、能锁屏认证、能加密存取数据、能在特定
条件下**彻底销毁全部用户数据而保留系统本体**的操作系统内核态之外的安全子系统。

- 载体：本机 x86_64 用户态程序 `aether-os` + 一个隔离的「模拟整机磁盘」目录。
- 不是 Android 应用、不是 APK、不是虚拟机套壳预览包。**目标是刷入开发板与谷歌 Pixel
  真机实测**（2026-11-14 用户修订：早期「不刷真机、不发布」口径已推翻）；当前阶段仅在
  云电脑上做系统调试与构建，真机刷入为后续阶段，尚未执行。
- 磁盘根由 `--root` 指定（默认 `build/secure-root`），所有路径由脚本自身位置推导，
  不写 `/usr`、`/run` 等系统目录，也不会误伤工作区其它文件。

## 2. 威胁模型：这套系统到底在防谁

| 威胁 | 攻击方式 | 本系统的对策 |
| --- | --- | --- |
| 暴力破解口令 | 反复试口令 | 失败计数 + 指数退避 + 达阈值即销毁数据 |
| 重启绕过计数 | 试几次就重启，指望计数归零 | 失败计数每次立即原子落盘；另由只追加哈希链交叉核对 |
| 篡改计数文件 | 直接改 `auth.state` 把失败数清零 | 计数文件带设备密钥 HMAC；改了会被判定篡改（篡改即擦） |
| 连 MAC 一起重算 | 读得到 `sys/device.key`，重算 HMAC 后改计数 | 审计链里的失败事件独立计数，加载时取两者较大值 |
| 胁迫解锁 | 被逼说出/输入口令 | 胁迫口令（duress）：输入即触发销毁 |
| 系统被篡改 | 改系统文件、植入后门 | 系统区完整性基线 + 开机自检，异常按配置触发销毁 |
| 断电半写 | 写状态文件时掉电留下半截数据 | 临时文件 → fsync → rename → 目录 fsync 原子路径 |
| 密钥残留在内存/交换区 | 从内存或 swap 捞 DEK | DEK 仅解锁后驻内存并 `mlock`，锁定/擦除/退出时强制清零 |
| 数据「删了但能恢复」 | 恢复出厂只删索引，底层密文还在 | 销毁 DEK（crypto-shred）+ 4 轮覆写整卷 + 删除全部用户态残留 |
| 事后抵赖/伪造证据 | 否认销毁发生过、篡改日志 | 只追加哈希链审计 + 可离线校验的销毁证明 |

## 3. 磁盘三分：这是「数据全抹除、系统不抹除」的地基

运行根下四个区，语义严格区分：

| 区 | 内容 | 擦除时的行为 |
| --- | --- | --- |
| `sys/` | 系统本体：`aether.bin`、`init.aether`、`brand.txt`、`device.key` | **绝不写、绝不删**；擦除前后整体摘要必须逐字节一致 |
| `data/` | 用户全部数据：`auth.state`（凭据与计数）、`vault.key`（密钥包装材料）、`vault.img`（4 MiB 加密卷） | **全部销毁**：卷多轮覆写，其余覆写后删除 |
| `journal/` | 只追加防篡改审计哈希链 `chain.log`、完整性基线 `integrity.baseline` | 只追加销毁事件，不清空、不覆写 |
| `receipt/` | 销毁证明 `wipe-<seq>.json` | 只新增，作为系统级取证保留 |

> 关键不变式：自毁引擎内**不存在**对 `sys/` 的删除或覆写调用；擦除结束时会重算
> `sys/` 摘要并与擦除前比对，不一致即判定 FATAL 并在证明里写 `sys_unchanged: false`。
> 该断言由 `secure/tests/test_secure.c` 组 D 实测覆盖。

## 4. 密码学基座（`secure/core/aether_crypto.c`）

纯自包含 C 实现，无外部链接依赖，严格遵循公开标准：

| 原语 | 标准 | 用途 |
| --- | --- | --- |
| SHA-256 | FIPS 180-4 | 摘要、审计链、完整性基线 |
| HMAC-SHA256 | RFC 2104 | 计数文件 MAC、口令派生、密封认证标签 |
| PBKDF2-HMAC-SHA256 | RFC 2898 | 口令验证哈希（10 万次）、KEK 派生（20 万次） |
| ChaCha20 | RFC 8439（IETF 96-bit nonce） | 数据卷流加密 |
| encrypt-then-MAC | 自研组合 | `ae_seal/ae_open`：`nonce‖密文‖tag`，先验 tag 再解密 |

**不是玩具算法**：内置标准测试向量断言，并由本机 `openssl(1)` 独立复算交叉验证
（SHA-256 / HMAC / PBKDF2 / ChaCha20 keystream 四项逐字节一致，见
`evidence/round-002/openssl-crosscheck.txt`）。口令与密钥永不以明文落盘。

## 5. 认证引擎

- 口令只存 `盐 + PBKDF2-HMAC-SHA256(口令, 盐, 100000)` 的 32 字节哈希。
- 每次认证单次派生、常量时间比较（`ae_ct_eq`），避免时序侧信道。
- **失败计数三重防护**：
  1. 每次失败立即原子落盘（防重启/断电绕过）；
  2. `auth.state` 带设备密钥 HMAC，改计数即判篡改；
  3. 只追加哈希链里的 `AUTH_FAIL` 事件独立计数，重新加载时取两者较大值——
     即便攻击者连 MAC 一起重算，也绕不过审计链（组 E 实测）。
- 指数退避：第 n 次失败后延迟 `min(2^(n-1), 8)` 秒（自动化测试可用 `--no-delay` 关闭）。
- 会话空闲超时自动锁定；锁定即清零内存 DEK。
- **胁迫口令**：初始化时可设第二个口令，输入它不解锁任何数据，而是立即触发销毁。

## 6. 加密保险库（全盘静态加密）

```
DEK  = 32 字节随机数据加密密钥（永不落盘）
KEK  = PBKDF2(口令, kek_salt, 200000)
vault.key = "KEY1" ‖ ae_seal(KEK, DEK)          ← 被包装的 DEK
vault.img = "AEVL" ‖ blob_len ‖ ae_seal(DEK, 文件表) ‖ 0填充
```

- 文件表序列化后整体用 DEK 密封（AAD 绑定 `aether-vault-v1`），密文落盘；
  卷内不出现任何用户明文（组 D 用 `memmem` 全卷搜索验证）。
- 解锁成功后才把 DEK 解封进内存（`mlock` 防换出）；退出 / 锁定 / 擦除即 `ae_zero` 清零。
- 因此**销毁 `vault.key` 就等于瞬间让全部历史密文永不可解**（crypto-shred），
  再配合多轮物理覆写，构成双重不可逆。

## 7. 自毁引擎（本系统最核心的机制）

触发路径共四条，全部汇入同一个 `ae_secure_wipe()`：

| 触发 | 条件 | 返回值 |
| --- | --- | --- |
| 口令错误达阈值 | `fails >= max_fails`（默认 5，可配） | `AE_UNLOCK_WIPED` |
| 胁迫口令 | 输入 duress 口令 | `AE_UNLOCK_DURESS` |
| 紧急一键 | `panic` 命令 | 直接销毁 |
| 系统/计数篡改 | 开机自检或认证路径检出异常，且 `tamper_wipe=1` | `AE_UNLOCK_TAMPER` |

销毁流程（真实实现，非占位）：

1. 审计链记 `WIPE_BEGIN`；立即清零内存 DEK、强制上锁。
2. 取证：记录 `sys/` 摘要、擦除前一刻的卷哈希。
3. **crypto-shred**：`vault.key` 等密钥材料覆写后删除，DEK 从此不可解。
4. **4 轮覆写整卷**（`0x00 / 0xFF / 随机 / 0x00`），每轮全卷 `fsync`；
   `auth.state` 等其余用户文件逐个覆写后删除。
5. **硬断言**：重算 `sys/` 摘要，与擦除前比对，必须逐字节一致。
6. 清除全部认证凭据与计数，进入 `FACTORY` 出厂态（数据清空、等待重新设置口令）。
7. 审计链记 `WIPE_DONE`，生成可离线校验的销毁证明 `receipt/wipe-<seq>.json`。

销毁证明包含：触发原因、时间戳、卷大小、覆写轮数、卷哈希前后值、`sys/` 摘要前后值、
`sys_unchanged` 布尔、审计链 head 前后值、结论
`ALL_USER_DATA_DESTROYED_SYSTEM_INTACT`。系统本体完好，仍可开机自检、重新初始化后继续使用。

> 与「恢复出厂设置」的区别：不是删索引/清标记，而是**销毁密钥 + 多轮覆写 + 清除凭据**，
> 并留下机器可判的不可逆证据。擦除后用原口令重新初始化，旧文件也读不回来。

## 8. 审计哈希链与系统完整性

- 每行 `seq|ts|event|detail|prev_hash|hash`，`hash = SHA256(prev_raw ‖ body)`，
  创世 `prev` 为全 0。改/删/插任意一行，后续链必断，`ae_audit_verify()` 检出。
- 只记事件类型与中性描述，绝不写口令、密钥、用户文件明文。
- 系统区完整性基线锚定在 `journal/`（只追加区，不在用户数据擦除范围内），并写入审计链，
  攻击者无法「改系统文件后顺手改基线」而不留痕。
- 每次开机自检：审计链校验 + 完整性比对；异常按配置触发销毁。

## 11. 诚实边界（未做 / 待办）

- **这是云电脑上软件模拟的用户态安全整机**，不是刷入真机的内核；S6 真机移植未开始。
  真机上「防篡改计数」应由 TEE / 安全芯片锚定，当前用 `sys/device.key` + 审计链
  做软件模拟等价物，强度不等同于硬件根信任，如实标注。
- **覆写的物理语义**：当前卷是本机文件系统上的定长文件，多轮覆写针对该文件；
  对真实 SSD 的 FTL 磨损均衡 / 稀疏文件物理块，需要真机上的 `BLKDISCARD` / 安全擦除命令，
  留待真机阶段。
- **安卓兼容层**：按约定的「卓易通」形态属于主系统内的独立容器子系统，
  当前 `android-compat/` 验证线已能做到 `sys.boot_completed=1`，但 `pm install` 第三方
  APK → 出帧 → 可交互尚未坐实；本轮聚焦安全本体，**兼容层未改动、未接入擦除引擎**，
  其独立数据分区不在当前 `data/` 擦除范围内。这是明确的待办，不虚报为已完成。
- **系统界面图**是真实状态快照的可视化（取证用），不是已跑通的图形桌面帧缓冲；
  图形桌面与输入桥属 B 轨后续工作。
- **命名**「长明」为预留，未注册公司、未注册商标、未改仓库对外品牌字样。
