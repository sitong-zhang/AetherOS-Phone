## 0. 先更正我上一轮的一处误判（重要）

上一轮我初读报告时，曾把 §4.1「设计意图（USB 插入/拆机不删、触及核心数据+攻击意图才删）」
判为**「与用户原话冲突、驳回」**。这是错的。

用户 2026-11-14 明确澄清：

> 「就是他这里面说的问题，就是那个插USB还有系统转接的那个，**和我的意思一样**，
> 我的意思可能没给你说明白，正常维修手机进行某些地方的短接，不会删除系统，
> 但是如果触及到用户数据和系统核心数据的短接USB插入，**如果检测到攻击意图**，
> 就立刻摧毁系统，然后烧毁硬件。」

即：用户真实意图**一直是「事件只作证据，行为/攻击意图才触发」**，是我此前把「USB 强插 /
拆机 / 短接 → 立刻抹除」这句原话**过度字面化**成了「插一次就删」，做成了 `ae_ld_on_event()`
里 LOCKED 态「三个事件到达即 brick」。

**结论：报告 §4.1 / §4.2 / §4.3 修改 1 / §4.5 的分级方案全部采纳**，我上一轮的驳回作废。
报告 §4.2 指出「代码实现与设计意图不一致」这条缺陷**成立**，是本阶段最该先改的逻辑缺陷。

## 2. 最关键的一处判向纠正：报告评错了对象

报告从 §2 到 §5.5 把 `kernel/`（自研 x86_64）当作**本项目的产品内核**来评分、列 P0、排修复优先级。
这与 V2 总纲、AGENTS.md、以及用户两次把我拉回来的指令**直接冲突**：

- V2 §1.1、开发提示词第 168 行明确「**不自研内核，以成熟开源内核为底**」；
- AGENTS.md：产品 = **ARM64 Linux 6.6.70 内核 + 完全自研用户态**；
- 用户 11-14 原话：「**这是基于 Linux 内核系统构建的手机操作系统，主打安全，之前那个总规划(V2)你难道忘了吗**」。

因此：

| | 报告默认 | 事实 |
|---|---|---|
| 产品内核 | 自研 x86_64 `kernel/` | **Linux 6.6.70 (ARM64)** |
| `kernel/` 定位 | 产品内核、评 P0 | **研究性 R&D 教学内核，非产品**，其 V1–V16 缺陷已知、已如实降级标注 |
| V1「ring3 任意读写内核内存」 | 产品致命漏洞 | R&D 内核的练习缺陷；产品侧由 **Linux 用户指针校验 / 页表隔离 / 异常分流**保证，**不需要也不应该**在 R&D 内核里重造 |

**处置**：V1–V16 的洞「技术属实」，我**不否认其存在**，也已在顶层文档醒目化「`kernel/` 非产品内核」以防后续评估再错位；但**不投入修复 R&D 内核**，因为那正是用户两次拽回来的死路（在自研内核里补 Linux 已有的能力）。报告 §5.5 的修复优先级表据此驳回。

> 这一条正是「自行判断是非对错」：报告是一份扎实的独立实测，但它评的对象和产品的真实
> 架构不是一回事，不能因为 PoC 跑得漂亮就把整个产品方向带回去重造内核。

## 5. 诚实边界（不实称）

- 云端「烧毁硬件」= **仿真熔断指令锁存**（`ae_hal_hw_fuse_backend()` 返回 `simulated(cloud-no-physical-fuse)`），
  不是真的烧 eFuse；真机物理永久变砖需 S6 接 Titan M / eFuse / crowbar。
- 软件熔断 = 删分区 + BRICKED 标记 + 引导级拦截，**系统本体不可恢复但刷机可重装**，不叫硬件永久变砖。
- 物理检测（USB/开盖/短接）在云电脑是**故障注入仿真**，不是真的电气/霍尔/防拆检测。
- `secure/` 仍是 **x86_64 本机 CLI**，非随 Linux 手机 OS 启动的服务；H1–H4（验证启动/故障隔离/地址隔离/内核硬化）属 Linux 内核层，**未开始**。
