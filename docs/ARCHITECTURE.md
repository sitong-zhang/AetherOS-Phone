# AetherOS 架构（v2 口径）

> 本文档描述**目标架构与当前进度**。状态只能由证据提升；未跑通一律写「部分实现 / 未开始」。
> 唯一需求源为《AetherOS 需求总文件 v2》。本仓库早期的「自包含 APK 内嵌虚拟机」是历史
> 交付形态，已归档停用，不再是当前架构（见 `vm/DEPRECATED.md`）。

## 一、交付形态

AetherOS 是在云电脑上用软件模拟真实运行的移动操作系统整机：真实开机、真实出图、真实
响应输入。系统本体不是 Android 应用、不是 APK、不是虚拟机套壳、不是「装个 App 看效果」的
预览包。内核基于 Linux 且从源码构建；用户态（init、服务、合成器、框架、界面）完全自研，
不基于 AOSP、不基于任何现成发行版。

对既有应用格式的兼容由系统内独立子系统以容器化方式提供（可基于 AOSP / LineageOS /
Waydroid 等开源实现），与主系统自研不冲突。

## 二、双轨（§2.6）

云电脑无 `/dev/kvm`、vmx/svm 计数为 0（实测见 `docs/00-BASELINE.md`），整机只能用
QEMU TCG 纯软件模拟。TCG 下 ARM64 整机启动按分钟计、交互帧率不足 1fps，用它做「动效跟手」
验收不成立；反过来只用原生跑上层又证明不了「内核能起来」。因此拆成两条轨道：

| | A 轨 · 整机链路 | B 轨 · 交互与像素 |
| --- | --- | --- |
| 载体 | QEMU ARM64 + TCG，自建内核 + 自建根文件 | **同一份上层源码** x86_64 原生构建，接口层接仿真实现 |
| 证明 | 引导 → 内核 → init → 服务 → 合成器首帧 → 一次注入输入改变画面 | 交互延迟、动画帧率、布局、对比度/遮挡/裁切、状态机、长稳 |
| 不证明 | 帧率、动效手感、长稳、并发 | 内核启动、真实驱动 |
| 证据 | 冷启动到首帧耗时、首帧后连续 N 帧不同、输入引起可验证画面变化 | §15 全部机器断言 |

**代码同源铁律**：A/B 两轨必须是同一份上层源码，差异只在构建目标与接口实现选择。若为在
B 轨跑起来而给上层加 `#ifdef` 或改调用方式，判接口层不合格，回头改接口层。每次提交两轨
各出一份证据，缺一即视为该阶段未完成。

## 三、八层（§4.1）

| 层 | 名称 | 职责 | 本仓库落点 | 当前状态 |
| --- | --- | --- | --- | --- |
| L0 | 引导与固件 | 启动环境、镜像加载、校验、分区、失败回滚 | 待建 | 未开始 |
| L1 | 内核 | 调度、内存、IPC、文件系统、网络、驱动框架、电源、安全、调试 | Linux 源码构建，待建 | 未开始 |
| L2 | 接口层（HAL） | 屏蔽硬件差异，向上提供统一能力接口 | `l2/` | 部分实现（本阶段核心） |
| L3 | 系统服务 | init、包管理、通知、媒体、音频、相机、位置、电话、网络、时间、更新、日志、电源等 | `guest/src/aether-init.c`、`aetherosd.c` 等 | 部分实现（待经 L2 解耦） |
| L4 | 图形与合成 | 显示管线、合成器、图层、帧调度、渲染原语、文字、图标、材质、转场 | `guest/src/aether-compositor.c`、`aether-render.c`、`aether-material.c` 等 | 部分实现 |
| L5 | 框架与运行时 | 服务发现、应用生命周期、窗口、输入分发、资源、权限、运行时 | `guest/src/` 业务层 | 部分实现 |
| L6 | 界面系统 | 设计语言、组件库、系统界面、系统应用 | `guest/src/aether-phone.c`、`aether-ui.c` 等 | 部分实现 |
| L7 | 生态与工程 | 商店、签名、沙箱、兼容层、工具链、构建、CI、测试、文档 | `tools/`、`scripts/`、`docs/` | 部分实现 |

### 分层铁律（§4.2）

1. 跨层只能通过显式接口；禁止跨层直调内部函数。
2. 硬件访问只能发生在 L2 及以下；L3 以上不许出现设备节点路径、寄存器地址、厂商私有调用。
3. 上层不得感知「当前是云端还是真机」，只感知接口能力。
4. 每层必须有独立可运行的测试入口。
5. 第 2 条必须机器可检（§5.6），不靠自觉。

> **现状差异（如实记录）**：历史 `guest/src/` 中仍有 13 个 C 文件直接打开 `/dev/` 或读
> `/proc/`（显示后端、合成器、系统指标、安卓桥等）。按 §5.6 第一条机检，这属于不合格，
> 是 S2 阶段必须整改的项。机检脚本会如实报出命中，不因「能跑」而豁免。

## 四、L2 硬件接口层（§5，本阶段核心）

```
上层（服务 / 框架 / 界面）
        ↓ 调用统一接口（能力查询 + 错误码 + 流控 + 状态）
接口层（定义能力，不含实现）         ← l2/include/
        ↓ 按配置选择
仿真实现（A/B 轨）  或  真机驱动（S6） ← l2/sim/
```

**十五个域（§5.2，一项不可缺）**：显示、输入（触摸/按键）、音频、相机、Wi-Fi、蓝牙、
蜂窝/基带、定位、传感器、生物识别、电源与电池、热管理、存储、网络（通用）、时钟/RTC。
每个域接口必须提供：**能力查询 + 错误码 + 流控计数**三件套；云端给出仿真实现（内存帧缓冲、
脚本注入、虚拟音频/网络、完整基带状态机等）；真机阶段按承诺度换实现（S6 只承诺七域真机
可用，其余标注「仅仿真」并写清原因，不许写成已支持）。

**流控与背压（§5.3）**：帧提交、输入事件、音频、相机、网络、日志、存储、基带、电源、
传感器都必须有明确的排队/丢弃/阻塞策略、上限、计数与查询入口。关键边界事件（按下/抬起、
注册失败、掉电、状态跳变）绝不许丢；降频必须上报，不许悄悄变低。

**接口自证（§5.4）**：不启动整机界面，直接对每个接口做高频、超时、断开、异常返回、
并发调用测试；支持全仿真/部分仿真/真机实现切换；可主动注入失败、延迟、断连；缺实现或
实现报错时系统明确提示并降级运行，不白屏、不死机、不静默失败。

## 五、机检门禁（§5.6）

把「自觉」换成「脚本必过」：

| 门禁 | 检查方式 | 不通过判据 |
| --- | --- | --- |
| 无设备路径上浮 | 扫 L3 以上源码，禁止 `/dev/`、`/sys/class/`、`/proc/` 直连 | 命中即失败 |
| 无跨层直调 | 文件头部声明的依赖之外出现 include / 符号引用 | 命中即失败 |
| 接口覆盖 | 每域必须有「能力查询 + 错误码 + 流控计数」三件套符号 | 缺项即失败 |
| 实现可替换 | 编译两次（仿真/桩实现），上层目标文件哈希一致 | 不一致即失败 |
| 单一参数源 | 业务代码出现裸数值字号/间距/时长/尺寸（非来自参数源） | 命中即失败 |

门禁脚本由 `scripts/aether.sh test` 统一调用，结果写入 `evidence/`。**验收标准、门禁脚本、
断言阈值不由执行方修改**（§11.3 红线）；要改只能提变更申请，附理由与证据。

## 六、阶段与门禁（§6）

| 阶段 | 目标 | 结束标志 |
| --- | --- | --- |
| S1 环境打通 | 一键起停重建，A 轨到首帧 | 连续三次重建一致；首帧后连续帧变化可证 |
| S2 接口层成型 | 十五域抽象 + 仿真实现 | 接口自测全绿；切换实现不改上层；五门机检全过 |
| S3 整机闭环 | 引导到桌面全通 + 输入可用 | 全流程自动跑通；**软键盘可用（含中文），一票否决** |
| S4 能力补齐 | 模块清单补齐 | 清单无缺项，逐模块可交互且过像素断言 |
| S5 稳定与性能 | 长稳、性能、异常恢复 | 长稳通过；六类异常可自动发现；性能可对比 |
| S6 真机移植 | 换实现层上真机 / 树莓派 | 上层零改动；可刷可回滚；七域真机可用 |

门不过不进下一阶段；仿真通过不等于真机通过，两条证据分开记。

## 七、参数治理（§10.2）

- 唯一参数源：`guest/src/aether-tokens.h`（布局令牌 `TK_*`）与
  `guest/src/aether-glass-spec.h`（光学常量）。业务代码不许出现裸数值。
- 每个参数注明「在哪台设备、什么分辨率、实测为什么取这个值」。
- 改参数必须附前后帧/帧时对比，随提交归档。
- 需求只写「要什么效果」，数值只出现在参数源与实测报告里。

## 八、启动链（目标形态，A 轨）

```
QEMU ARM64 (TCG) → 自建 Linux 内核 → 自有 init → 服务编排
   → L2 仿真实现（帧缓冲/输入注入）→ 合成器 → 锁屏/引导页 → 桌面
```

内核与根文件系统从源码构建，或提供带校验和的获取脚本；构建脚本不许依赖机器绝对路径
或系统目录写权限（实测历史脚本硬编码 `/root/aether-archive/...`，属待整改项，
见 `docs/00-BASELINE.md` 差异第 4 条）。

## 九、真机路线（§3.2 / §12，下一阶段）

云端 S1–S5 全部通过、上层代码稳定后才上真机。选型硬条件是**主线 Linux 已有该机端口**
（内核 defconfig + dtb + 显示/触摸可用），而非「能解锁」；官方工厂镜像只用于回滚到安卓。
真机阶段只允许改接口实现层，不允许改界面、服务、框架的调用方式。副目标为树莓派，
证明「换硬件只换实现」。

## 十、安全子系统（`secure/`，本轮已跑通）

安全是系统主打特性。`secure/` 是一套独立编译运行的**用户态安全整机本体**，与 L0–L7
分层正交，不依赖 `l2/` 或 `guest/` 图形栈：

```
aether-os（整机入口 / 交互 shell）
  ├─ 认证引擎 ─ 口令哈希 / 失败计数(原子落盘 + HMAC + 审计链交叉核对) / 退避 / 空闲锁定
  ├─ 加密保险库 ─ DEK(随机, 仅内存) ← KEK(口令派生) 密封；数据卷 ChaCha20+HMAC 静态加密
  ├─ 自毁引擎 ─ crypto-shred + 4 轮覆写 data/ + sys/ 摘要硬断言 + 销毁证明
  ├─ 审计链(journal/) ─ 只追加哈希链，防篡改
  ├─ 完整性(sys/) ─ 基线锚定，篡改即擦
  └─ 隔离存储 ─ sys/(系统) | data/(用户数据) | journal/(日志) | receipt/(证明)
```

**不变式**：自毁引擎作用域严格限于 `data/`；擦除前后 `sys/` 摘要必须逐字节一致。
设计、威胁模型与 14 项特性见 [`SECURITY.md`](SECURITY.md)，验收与证据见
[`02-SECURE-REPORT.md`](02-SECURE-REPORT.md) 与 `../evidence/round-002/`。

> 边界：这是云电脑软件模拟的用户态安全子系统，不是刷入真机的内核；真机阶段需用
> TEE / 安全芯片锚定失败计数、用块设备安全擦除命令替代文件级覆写。安卓兼容层容器
> 尚未接入该擦除引擎，属明确待办，不虚报为已完成。
